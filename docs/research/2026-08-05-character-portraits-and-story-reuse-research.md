## 1. Player character creation: free-form vs. AI-predefined-with-portrait

**Finding: no comparable shipped or open-source AI-narrative product solve "free-form player character with portrait staying consistent across independently generated images" — entire ecosystem either sidesteps problem (fixed pre-authored portrait) or accepts prompt-discipline drift. Real evidence tradeoff structural, not execution gap unique to this project.**

### AI Dungeon (Latitude) — customization choice-based, not free-text
AI Dungeon's own help docs distinguish two mechanisms, neither "type your own character freely":
- **Character Creator Scenarios**: "allow players to customize their character by picking pre-determined options (rather than writing in their answer), with the Opening Prompt built with those choices in mind." Customization real but constrained to author-defined choice sets.
- **Default/Story Scenarios**: fixed starting prompt, "will always start the exact same, no matter who plays it."
Source: [AI Dungeon Help — Creating Character Creator Scenarios](https://help.aidungeon.com/faq/whats-the-difference-between-scenarios-and-worlds) · [AI Dungeon Help — What are Scenarios?](https://help.aidungeon.com/faq/what-are-scenarios)

### NovelAI — character consistency solved by prompt discipline, not infra
NovelAI's own docs for creating consistent character across separately generated images explicit: mechanism is **tag density in prompt, not image-to-image, embeddings, or LoRA training**: "the more tags we use to describe our character's outfit, the more consistent it will stay across different images." Guide walks through iteratively adding clothing/detail tags until character reads stable across separate generations — author-discipline technique, not technical guarantee.
Source: [NovelAI Docs — Creating Consistent Characters](https://docs.novelai.net/en/image/tutorial-charactercreation/)

### Character.ai/SillyTavern-style "Character Card" ecosystem — strongest evidence for predefined-portrait pattern
De facto interchange format across entire product category (SillyTavern, Character.ai-adjacent tools) is **Character Card V2 spec**. Primary-source GitHub spec defines card fields — `name`, `description`, `personality`, `scenario`, `first_mes`, `mes_example`, `system_prompt`, `alternate_greetings`, `character_book`, `tags`, `creator`, `character_version`, `extensions` — **no dedicated avatar/image field at all**. Distribution unit itself PNG file with JSON embedded in `tEXt` metadata chunk — portrait IS container, one fixed pre-authored image per character, shared identically by every user loading that card. No per-user or per-session portrait regeneration anywhere in format.
Source: [malfoyslastname/character-card-spec-v2 (GitHub)](https://github.com/malfoyslastname/character-card-spec-v2)

### Open-source "AI Dungeon Master" projects — closest architectural analogs
- **NarrativeEngine-P** — self-hosted, works with "any OpenAI-compatible LLM," closest architectural sibling to this repo's own self-hosted LangGraph.js plan. Character creation fully free-form, conversational: "Start a new chat... The GM will walk you through character creation and then drop you into the world." Does generate portraits — but only for NPCs ("Generate NPC portraits on the fly in 5 art styles... Works with any OpenAI-compatible image API"). README makes no claim of player-character portrait generation at all. Directly comparable project choosing free-form text for player character specifically *because* ships portrait generation elsewhere (NPCs), didn't extend same feature to player.
  Source: [Sagesheep/NarrativeEngine-P (GitHub)](https://github.com/Sagesheep/NarrativeEngine-P)
- **DungeonGPT-JS** — free-form structured character-creation form (stats, class, race, background, alignment) plus "profile picture" field; README doesn't specify whether image AI-generated or user-supplied — open, undocumented point, not confirmed either way.
  Source: [EdwardAThomson/DungeonGPT-JS (GitHub)](https://github.com/EdwardAThomson/DungeonGPT-JS)
- **GameMasterAI** — README documents setup/dependencies only; no character-creation flow or portrait mechanism documented at all.
  Source: [deckofdmthings/GameMasterAI (GitHub)](https://github.com/deckofdmthings/GameMasterAI)

### CRPG contrast — different axis of tradeoff, not same problem
Baldur's Gate 3's Origin-character-vs-custom-Tav split UX/onboarding tradeoff, not art-generation-cost or consistency tradeoff (BG3 renders every character live in-engine, no generative-art-consistency problem exists there at all): "Larian encourages people to use Origin stories because many players new to cRPG genre feel uncomfortable not being handed a proxy character," while custom Tav trades authored reactivity for full creative control (can pick race/class no companion has). Useful as **narrative-design** parallel (predefined characters can carry richer, pre-written reactivity free-form character can't), but doesn't bear on image-consistency/cost question this project actually faces — noting axis mismatch explicitly rather than overreaching analogy.
Source: [TheGamer — Should You Pick An Origin Character Or Create Your Own](https://www.thegamer.com/baldurs-gate-3-choose-origin-character-or-create-your-own/)

**Verdict:** every comparable product either (a) fixes portrait once, never regenerates per-user (Character Card ecosystem — closest match to "AI-predefined-with-portrait"), or (b) keeps player character free-form, simply doesn't attempt player portrait at all (NarrativeEngine-P, closest architectural analog to this project). None demonstrates "free-form player character + consistently-evolving portrait" working in production. See Section 2 for whether specific models this project already chose (Decision #15) change that calculus.

## 2. Dynamic portrait evolution: does chosen v1 art stack support image-to-image editing on existing portrait?

**Finding: yes — both OpenRouter image models already locked in by Decision #15 (Gemini 2.5 Flash Image / Nano Banana, Seedream 4.5) document real image-to-image edit support via reference-image input parameter, at same flat per-image price as fresh generation. New information: Decision #15 chose these models for MVP art-gen cost, not edit capability — edit capability comes along free.**

### OpenRouter's unified Image API — `input_references` parameter
OpenRouter's own docs and tutorial blog (checked independently, two separate fetches, consistent result) describe dedicated image-editing path on `POST /api/v1/images`: `input_references` array of `{ type: "image_url", image_url: { url } }` objects, accepting either HTTP(S) URLs or base64 data URLs, "number of references accepted varies by provider." Explicitly framed as mechanism for "image-to-image work" — pass existing image back in alongside text prompt to get modified version, not just fresh text-to-image call. (One direct API-reference URL, `openrouter.ai/docs/api/api-reference/images/create-images`, 404'd on fetch — navigation gap this pass, not evidence against feature, since same parameter independently corroborated on two other OpenRouter-owned pages.)
Source: [OpenRouter Docs — Image Generation guide](https://openrouter.ai/docs/guides/overview/multimodal/image-generation) · [OpenRouter Blog — Image Generation API tutorial](https://openrouter.ai/blog/tutorials/image-generation-models/)

### Gemini 2.5 Flash Image ("Nano Banana") — edits confirmed on model's own page
OpenRouter's model card states directly: "It is capable of image generation, edits, and multi-turn conversations," and "[unlike] traditional image generators that often struggle with precise edits or maintaining consistency across variations, this model excels at targeted modifications while preserving the essence of your original content." Real-world usage cited same page: "generating hundreds of ad variations from single source image, maintaining brand consistency" — exact "take last image, apply targeted change, keep rest" shape this project needs for wound/armor updates.
Source: [OpenRouter — Google: Nano Banana (Gemini 2.5 Flash Image)](https://openrouter.ai/google/gemini-2.5-flash-image)

### Seedream 4.5 — multi-image reference input, same $0.04/image price as fresh generation
OpenRouter's Seedream 4.5 page confirms flat "$0.04/image" pricing (matching Decision #15's ~$0.04 target exactly) plus documents "multi-image composition capabilities... significantly strengthened" and "editing consistency" as explicit improvement area, multi-image reference input "enabling consistent identity, style, and proportions across a series of images" (corroborated by third-party reseller's description same model). OpenRouter prices per **output** image regardless how many reference images submitted as input — edit call costs same as fresh-generation call.
Source: [OpenRouter — ByteDance Seed: Seedream 4.5](https://openrouter.ai/bytedance-seed/seedream-4.5) · [kie.ai — Seedream 4.5 Edit](https://kie.ai/seedream-4-5)

### Per-image cost reconciliation
Gemini 2.5 Flash Image's cost token-metered, not flat, at provider level: Google's own developer pricing page states image output tokens $30/1M, ~1290 tokens per output image (up to 1024×1024) — **≈$0.039/image**, actual source of Decision #15's "~$0.04/image" figure for this model. (One OpenRouter page surfaced during research showed different figure, $0.30/$2.50 per 1M input/output tokens — likely stale scrape or different pricing view; Google's own developer pricing page more authoritative primary source here, reconciles with plan's existing number, so it's cited.)
Source: [Google AI for Developers — Gemini Developer API pricing](https://ai.google.dev/gemini-api/docs/pricing)

### Higgsfield's Soul ID — checked per task's request, not re-litigation of post-v1 deferral
Higgsfield has named, real feature for this exact problem class — **Soul ID** — but works on materially different mechanism than OpenRouter's per-call `input_references`:
- **Trained identity, not per-call reference.** "Give Soul ID a set of photos of one person, it learns that identity, and from then on it applies that identity to anything you generate." Contrasted directly against reference-image approaches in Higgsfield's own framing: reference image "anchors a single generation but drifts across many separate ones," while Soul ID "trains a reusable identity once, then holds it across every generation... without re-uploading."
- **Setup cost:** 20+ reference photos, "about 3 to 5 minutes" training time — real per-character setup cost per-call reference-image approach doesn't have.
- **Platform lock-in:** trained identity "lives in the Higgsfield ecosystem," "used inside Soul 2.0 and connected tools, not exported as standalone model file."
- **Not documented as incremental-edit/inpaint tool.** Nothing in available Soul ID docs addresses adding wound or new armor piece to already-generated image specifically — feature's own framing "endless stream of content across outfits, settings, aesthetics" (fresh generations sharing identity), not "edit this one existing image."
- **Pricing:** no first-party price found on Higgsfield's own indexed API docs (`docs.higgsfield.ai`'s documented sections: Generate Images from Text / Generate Videos from Images / FAQ / Support / How to use API / Client Libraries / Webhook Integration / Introduction — no Soul, Soul ID, pricing page appears in that index). Third-party API resellers (WaveSpeed, Segmind, Eachlabs) quote Soul-family image generation $0.09-$0.23/image range depending on variant — several times OpenRouter's flat $0.04, figure reseller-sourced not Higgsfield first-party, treat as directional only.
Source: [Higgsfield Blog — Soul ID: AI Character Consistency](https://higgsfield.ai/blog/Soul-ID-AI-Character-Consistency) · [Higgsfield Blog — How to Keep AI Persona Consistent Using Higgsfield Popcorn](https://higgsfield.ai/blog/how-to-keep-ai-persona-consistent-higgsfield-popcorn) · [WaveSpeedAI — Higgsfield Soul Image-to-Image](https://wavespeed.ai/docs/docs-api/higgsfield/higgsfield-soul-image-to-image)

**Verdict:** "character sheet drives live portrait updates" v1-feasible on already-chosen OpenRouter stack, at already-budgeted ~$0.04/image cost, using `input_references` edit path instead of fresh text-to-image call each time — needs implementation task (prompt-template + reference-image passthrough, alongside T13's STYLE FORMULA work), not new architectural decision. Real open risk **identity drift across many sequential edits** (does turn 40's portrait still look like turn 1's character after 39 incremental edits?) — empirical question to validate in T22's harness, not something docs above answer definitively. Higgsfield's Soul ID real, differently-mechanized fallback if drift proves unworkable (train-once identity vs. re-submit-last-image-every-time), at real cost premium and platform lock-in — worth naming as fallback option, not worth reopening Decision #15's deferral on evidence gathered here.

## 3. Story reuse across users: does LangGraph.js's checkpointer support forking/cloning thread?

**Finding: no — not in self-hosted LangGraph.js + `PostgresSaver` setup this project already adopted (Decision #21). One primitive that does exist for exactly this purpose — `copy_thread` — is LangGraph **Platform** (hosted product) feature, exact product Decisions #19/#21 explicitly rejected favoring self-hosting. "Design your own Postgres schema on top" situation, confirmed rather than assumed.**

### Checkpointer interface itself has no clone/copy method
`BaseCheckpointSaver` interface (which `PostgresSaver` implements) documented as four core methods: `.put` (store checkpoint), `.putWrites` (store pending intermediate writes), `.getTuple` (fetch checkpoint by `thread_id`/`thread_ts`), `.list` (list checkpoints matching filter). No duplicate/clone/copy operation exists on this interface.
Source: [LangGraph.js API Reference — `@langchain/langgraph-checkpoint`](https://langchain-ai.github.io/langgraphjs/reference/modules/langgraph-checkpoint.html)

### docs.langchain.com's own Persistence guide doesn't offer one either
Persistence guide lists checkpointer use cases as "conversation continuity, human-in-the-loop workflows, time travel, and fault tolerance." "Time travel" here means replaying/branching **within** single `thread_id`'s own checkpoint history (e.g. resuming from earlier checkpoint after error) — not documented as way to copy state into **different** `thread_id` for different user/session, which is what story-reuse-across-users actually requires.
Source: [Docs by LangChain — Persistence (JS/LangGraph)](https://docs.langchain.com/oss/javascript/langgraph/persistence)

### Primitive that does this exists — but only on LangGraph Platform
LangGraph Platform's Threads API exposes exactly operation this project wants: `POST /threads/{thread_id}/copy`, wrapped by SDK as `client.threads.copy(thread_id)` — "creates an independent thread whose history is identical to the original thread at the time of copying." Confirmed via official LangChain community forum (two separate threads: one explicitly asking how to do this in self-hosted OSS, second reporting Platform copy operation taking 12+ minutes on large threads in production) and `langgraph-sdk` reference docs for `Thread`/`ThreadsClient`. **This Platform-only.** Decisions #19 and #21 already committed this project to self-hosted LangGraph.js inside NestJS/Docker Compose specifically to avoid Platform's external infra dependency and cost — so primitive not available to this project as architected.
Source: [LangChain Forum — How to clone a thread in LangGraph](https://forum.langchain.com/t/how-to-clone-a-thread-in-langgraph/2764) · [LangChain Forum — LangGraph thread copy can take 12+ minutes](https://forum.langchain.com/t/langgraph-thread-copy-can-take-12-minutes-recommended-production-pattern/3763) · [LangChain Reference — `ThreadsClient`](https://reference.langchain.com/python/langgraph-sdk/_async/threads/ThreadsClient)

### Self-hosted OSS has no supported workaround — only raw-SQL one
Same forum thread, only workaround offered for self-hosted OSS manual and unsupported: `PostgresSaver`'s underlying tables (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs`, keyed by `thread_id`) can in principle be copied row-by-row with `thread_id` rewritten to new value — described in forum as "just a matter of copying the rows and changing `thread_id` value to sth else," i.e. raw SQL operation project would own itself, not documented or supported LangGraph API. (Table names here sourced from community forum answer, not first-party schema reference fetched directly this pass — flagging distinction rather than presenting table names as independently primary-source-verified.)
Source: [LangChain Forum — How to clone a thread in LangGraph](https://forum.langchain.com/t/how-to-clone-a-thread-in-langgraph/2764)

**Verdict:** confirmed, not assumed — LangGraph.js's checkpointer has no built-in forking/cloning primitive in this project's actual (self-hosted) configuration. Whatever "flag good chronicle as reusable starting scenario for other players" feature gets built has to be application-level: bespoke Postgres table snapshotting relevant narrative state (not raw checkpoint-blob copy) when chronicle flagged, which *new* chronicle's `resolve`/`narrate` prompt context reads from at start — structurally same shape this project already adopted twice: `recall` node (Scope Decision #4 / T19, queries NPC/consequence table by `user_id`, injects prompt slot) and archetype art cache (Decision #6, keys off fixed taxonomy into Postgres-backed cache). Story reuse third instance of same "plain Postgres table feeds graph node's prompt context" pattern, not new mechanism.

## Recommendations for next `/plan-ceo-review` or `/plan-eng-review` pass

1. **Q1 (character creation):** Ship v1 with small set of AI-authored predefined characters (e.g. 4-8), each with **one** reference portrait generated once, offline — same mental model as Decision #6's archetype art cache, applied to player characters instead of monsters. Sidesteps industry-wide unsolved problem found in this research (no comparable product keeps *free-form* player character's portrait consistent across independent generations — Character Card ecosystem fixes portrait once per character; NarrativeEngine-P, closest open-source architectural analog, skips player portraits entirely). Defer free-form character creation with live portrait as distinct, harder post-v1 question — depends on Q2's per-edit drift risk actually holding up over many turns, unverified.

2. **Q2 (portrait evolution):** "Wound/armor updates reflected in character portrait" v1-feasible on already-chosen OpenRouter image stack (Decision #15) at already-budgeted ~$0.04/image cost — both Gemini 2.5 Flash Image and Seedream 4.5 support image-to-image editing via OpenRouter's `input_references` parameter, priced same as fresh generation. Doesn't require new provider or decision — implementation task alongside T13 (pass last-generated portrait URL as `input_references` entry instead of always generating from bare text prompt). Add explicit validation item to T22's harness: run portrait through several sequential edits, eyeball identity drift before committing this as live mechanic. Name Higgsfield Soul ID in TODOS.md as concrete (cost-premium, platform-locked) fallback if drift proves unworkable — without reopening Decision #15's existing Higgsfield deferral.

3. **Q3 (story reuse):** No LangGraph-native primitive exists for this in self-hosted LangGraph.js + `PostgresSaver` (confirmed against `docs.langchain.com` and LangGraph.js API reference, consistent with how Decisions #19-21 were originally verified) — `copy_thread` Platform-only, product this project already rejected. If scope accepted, should be scoped as own task (same shape as T19/T20): new Postgres table snapshotting flagged chronicle's reusable narrative state, read into new chronicle's `resolve`/`narrate` prompt context at start — no checkpoint-level cloning, no new service. Not blocking anything currently in flight; safe to leave unscheduled until persistent-world-memory (Scope Decision #4, post-v1) work actually underway, since shares same table-design pattern and timing makes sense to batch together.
